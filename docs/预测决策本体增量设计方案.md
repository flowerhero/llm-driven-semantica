# smini-extract 预测决策本体增量设计方案（提案 v1）

> 状态：**提案待认可**（用户确认决策点后实现；延续「契约即规则」哲学）。
> 目标：在五件套（实体-关系-属性-规则-流程）之上，为实现**本体驱动的预测与决策**，
> 再抽取六类信息——`states`（状态机）/ `functions`（函数指标）/ `temporal`（时序时态）/
> `actions`（动作处置）/ `constraints`（约束）/ `permissions`（权限），并增强
> `relations` 的传导语义。
> 依据：头条《Ontology时代下的：预测、推理、推演，决策，别搞混了》核心论断——
> **预测 = 某对象在某个时间窗内从状态 A 演化到状态 B**；静态本体回答"它是什么"，
> 动态本体回答"它将如何变化"。现有五件套已覆盖"是什么 + 怎么做"，缺"会怎么变 + 决策闭环"。

---

## 0. 设计立场（延续契约即规则）

- **LLM 全权语义、Python 惰性锚点**：六类新增全部由宿主 agent（豆包）按契约一次交卷；
  Python 只做确定性映射（字段校验、枚举兜底、下标/引用校验、ID 补算、统计登记），
  不判断语义。
- **新增即增量、旧契约不破坏**：`entities/relations/attributes/rules/processes` 原样保留；
  新增件套空数组合法（无该信息就不产出）。11 件套并存，向后兼容。
- **分界交给 LLM，Python 只兜底**：每个新件套与既有件套的语义分界写进提示词原则，
  不写可执行规则；Python 只在 schema 层校验枚举、在消费层兜底 `OTHER` 或丢弃非法引用。
- **不入图优先**：六类新增中仅增强型 `relations`（propagation）入实体-边图；
  其余均为独立产出（metadata 计数登记），保持图谱为"实体间事实"的纯净语义。

## 1. 本体论调研结论（六类的依据）

### 1.1 状态机（states）— 预测引擎

- **FSM / UML 状态机本体**：状态机由有限**状态（State）**、**事件（Event）**、
  **转换（Transition）**、**动作（Action）** 组成；转换带 **触发事件（trigger）**、
  **守卫条件（guard）** 与 **转换动作**（Transition: trigger [guard] / actionSequence，
  卡尔顿大学软件需求工程）。已有将 UML 状态机编码为 OWL DL + SWRL 的方案
  （Towards an Ontology for UML State Machines）——状态机可被形式化为机器可验证。
- **W3C SCXML**：transition 由事件触发、guard-condition 条件化、target 指定目标状态；
  状态可带 entry/exit actions。这是"状态迁移"的标准表示法。
- **文章对齐**："预测不是猜一个值，而是估计某对象在某个时间窗里会不会从状态 A 演化到
  状态 B"——**状态 + 迁移是预测的最小骨架**，`rules`（条件-动作）与 `processes`
  （活动序列）都无法直接表达"对象生命周期"。

### 1.2 函数指标（functions）— 机理可解释

- **SWRL（W3C）**：规则语言内建数学函数（swrlb:divide / multiply 等），可把
  "业务经验写成可计算函数"形式化，从基础属性**派生**新值。
- **OWL 定义类（Defined Class）**：含充要条件的类/属性，可用等价定义表达派生语义；
  本体形式化 `O=(C,I,P,A,F)` 中 F 即函数/规则集（《基于本体的物品属性类人认知及推理》）。
- **行业 ActionType/Function（ByteCloud、SuperML）**：Function 封装可复用的业务计算
  逻辑，挂载在对象上生成**虚拟/派生属性**，实现复杂指标动态计算。
- **文章对齐**："第二层函数指标特征（看机理）——把业务经验写成函数指标，如
  压力函数 = 需求强度 ÷ 供给能力"——函数是**推演**（"如果调整会怎样"）的输入，
  也是可解释性的来源（"为什么它危险"而不是黑盒分数）。

### 1.3 时序时态（temporal）— 时间维度

- **OWL-Time（W3C OWL 2 DL 本体）**：描述资源的时序属性——瞬时（instant）/区间
  （interval）、拓扑关系（before/during/overlaps）、时长（duration）、时点（position）。
- **双时态（bi-temporal，tOWL 等）**：区分 **valid time（有效时间）** 与
  **transaction time（事务时间）**；Welty & Fikes 以 TimeSlice + TimeInterval 给本体加
  时间维。
- **文章对齐**：预测输出第二项就是"时间窗（什么时候）"；坑 1 = "只做静态对象，
  不做时变状态"。监管文本的"自 2017-7-1 起实施""每年回访""新老划断"都是时态信息。

### 1.4 传导关系（propagation）— 系统性后果（增强 relations）

- **风险传导/依赖本体**：以**依赖边（dependency edge）** 表达跨系统依赖，边带
  **影响强度**与**衰减因子**（FactSet Revere 供应链：W_ij^(n) = α^n · R_ij）；
  沿依赖链逐跳传播计算风险（ArangoDB transitive-risk KG：风险沿关系逐跳传播）。
- **因果风险传染（arXiv 2407.17190）**：用结构因果模型（SCM）区分因果部分 X→Y，
  KG 表达风险传染路径。
- **文章对齐**："第三层关系传播特征（看传导）——上下游邻域风险聚合、关键路径长度、
  风险跨节点传递的速度与衰减"——这是预测准确性提升的关键（"哪里还没报警但已被影响"）。

### 1.5 动作处置（actions）— 决策落地

- **Palantir ActionType**：在本体层面定义"这个动作是什么、能对哪些对象/属性/链接做
  哪些变更"，执行时触发**副作用（side-effects）**（通知、链接创建/删除等）。
- **SuperML Action Types**：动作 = 类型化函数 + **前置条件（preconditions）** +
  状态变更 + 可选发出事件。
- **TAO（动作接口本体）**：动作语义动词必须与**效果**机械一致——定义 REQUIRED
  effects 与 FORBIDDEN effects。
- **文章对齐**：预测输出第五项"建议动作级别（观察/预警/干预）"；四层本体含
  "行动：可以执行什么、会产生什么副作用"。

### 1.6 约束与权限（constraints / permissions）— 决策可信与治理

- **SHACL（W3C Shapes Constraint Language）**：描述并约束 RDF 图内容——形状约束、
  **基数约束（minCount/maxCount）**、**值域/数据类型约束（datatype/nodeKind）**、
  不相交性（disjointness）。保证数据符合预期结构，是推理/决策可信的前提。
- **OWL 公理**：类不相交（disjointWith）、基数限制（cardinality restriction）、
  domain/range 约束——与 SHACL 互补的模式层约束。
- **行业四层闭环（data/logic/action/security）**：security 定义人和 AI 的操作权限
  边界，是"AI 真正介入业务做决策、做动作"的必要条件。
- **文章对齐**：决策不能基于非法状态（"不会基于非法状态决策"）；权限是决策自动化的
  治理边界。

## 2. 契约设计（六件套 + relations 增强）

**宿主交卷在五件套基础上新增以下数组，仍不含偏移、不含 ID、不含 object_literal：**

```
entities:   [{ surface, canonical, type }]                          # 原有
relations:  [{ subject, predicate, object, object_type, evidence,
               prop_kind?, strength? }]                              # 增强（见 2.1）
attributes: [{ entity, name, value, value_type, evidence }]          # 原有
rules:      [{ subject, condition, action, modality, evidence }]     # 原有
processes:  [{ name, description, steps, flows }]                    # 原有
states:     [{ object, name?, states[], transitions[] }]             # 新增①
functions:  [{ name, subject?, formula, inputs?, output_type, evidence }]  # 新增②
temporal:   [{ subject, kind, value, anchor?, evidence }]            # 新增③
actions:    [{ name, actor?, level, target?, side_effect?, trigger?, evidence }]  # 新增④
constraints:[{ subject, type, description, evidence }]               # 新增⑤
permissions:[{ actor, action, effect, scope?, evidence }]            # 新增⑥
```

### 2.1 relations 增强（传导语义，不加件套）

| 新增字段 | 含义 | 约束 |
|---|---|---|
| `prop_kind` | 关系类型子类，独立 4 类枚举 | `FACTUAL DEPENDENCY CAUSAL TRIGGER`；判不出省略（默认普通事实关系） |
| `strength` | 影响强度 | 可空；`HIGH/MEDIUM/LOW` 或原文数值/程度词 |

> 判定原则（写进提示词）：该关系是否承载**影响/依赖/因果/触发**语义——「依赖/
> 制约/传导/影响/导致/引发/触发」→ `prop_kind` 取相应值；传导链上的关系建议标
> `strength`（供下游图传播/风险传导用）。`prop_kind` 是**增强标注**，不改变关系的
> 实体-边图地位（仍入图，仅加边属性）。

### 2.2 states[]（状态机）

```
states: [{
  object,            # 状态机所属对象（实体 canonical，如「投资者」）
  name?,             # 状态机名（如「投资者身份状态机」），可空
  states: [          # 状态集合（有序，下标 0 起）
    { label, initial? }   # label=状态名（贴近原文）；initial=true 表示初始状态
  ],
  transitions: [     # 状态迁移
    { from, to,      # 引用 states 下标（整数 0-based）
      event?,        # 触发事件（可空）
      condition?,    # 守卫条件（可空）
      action?,       # 迁移动作（可空）
      evidence }
  ]
}]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `object` | 状态机主体 | 用实体 `canonical`（须与 entities 某条一致；引不到可用其他且容忍） |
| `states[].label` | 状态名 | **逐字/贴近原文**（如「普通投资者」「专业投资者」「C1」） |
| `states[].initial` | 是否初始状态 | 布尔；可空（默认 false） |
| `transitions[].from/to` | 迁移端点 | **整数下标**引用 `states`；越界**丢弃该迁移**（惰性锚点） |
| `event` / `condition` / `action` | 触发/守卫/动作 | 全部**可空**；event=什么事件触发，condition=满足才迁移，action=迁移时执行什么 |
| `evidence` | 原文短引用 | **逐字取自原文**，用于溯源 |

**分界原则（写进提示词）**：
- 文本描述**对象处于什么状态、在什么事件/条件下迁到另一状态**（生命周期、身份转化、
  等级调整）→ `states[]`。
- 与 `processes` 分界：`processes` 以**活动**为中心（谁按什么顺序做什么）；
  `states` 以**对象状态**为中心（对象如何演化）。同一句「普通投资者申请转化专业投资者」
  可同时产出 process（转化流程）与 states（身份状态机 普通→专业）。
- 与 `rules` 分界：`rules` 是条件-动作**规范**（该不该做）；`states` 的 transition
  表达**状态拓扑**（从哪到哪），transition 的 condition 只是守卫，不是规范义务。

### 2.3 functions[]（函数指标）

```
functions: [{
  name,              # 指标名（如「压力函数」「风险强度函数」）
  subject?,          # 挂载对象（实体 canonical，可空=全局指标）
  formula,           # 定义式/计算规则（LLM 用自然语言/运算符描述，声明式）
  inputs?,           # 依赖因子（其他实体/属性/函数名列表，可空）
  output_type,       # 输出类型，独立枚举
  evidence
}]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `formula` | 定义式 | LLM 声明式描述（如「需求强度 ÷ 供给能力」），**不强制可执行数学表达式** |
| `inputs` | 依赖因子 | 数组；元素可引用实体 canonical、属性名、其他函数名；**可空** |
| `output_type` | 输出类型，独立 7 类枚举 | `NUMBER PERCENT RANK BOOLEAN ENUM STRING OTHER`；判不出用 `OTHER`，不自创类型 |

**分界原则**：
- 文本给出**指标的计算定义**（"= 由…构成 / 按…计算 / 综合…得出"）→ `functions[]`；
- 与 `attributes` 分界：`attributes` 存**字面量值**（"回访比例=10%"）；
  `functions` 存**计算定义**（"压力 = 需求 ÷ 供给"）。同一指标可二者兼有
  （attributes 给当前值，functions 给定义式），由 LLM 判定各归其位。
- 与 `rules` 分界：`rules` 是条件-动作规范；`functions` 是**量化计算**，无道义模态。

### 2.4 temporal[]（时序时态）

```
temporal: [{
  subject,           # 主体（实体/规则/流程/状态的 canonical 或语义名）
  kind,              # 时态类型，独立 4 类枚举
  value,             # 时态描述（逐字取自原文）
  anchor?,           # 锚点时间（可空；DATE 实体 canonical，如「2017年7月1日」）
  evidence
}]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `subject` | 被限定的主体 | 用实体 canonical，或规则/流程/状态的语义名；**必填** |
| `kind` | 时态类型，独立 4 类枚举 | `VALIDITY FREQUENCY WINDOW TRIGGER`；判不出用 `VALIDITY` |
| `value` | 时态描述 | **逐字取自原文**（如「自2017年7月1日起实施」「每年」「未来2小时」） |
| `anchor` | 锚点时间 | 可空；DATE 实体 canonical |

**kind 枚举（时态类型，独立 4 类）**：
| 枚举值 | 含义 | 中文线索 |
|---|---|---|
| `VALIDITY` | 生效/失效区间 | 自…起实施/施行；有效期；截至… |
| `FREQUENCY` | 频率/周期 | 每年/每月/定期/每季度 |
| `WINDOW` | 时间窗/预测窗口 | 未来2小时/近期/下一时段 |
| `TRIGGER` | 触发时点 | 收到…时/当…时触发；申请时 |

**分界原则**：
- 文本对某事实/规则/流程给出**时间限定**（何时生效/多频繁/什么窗口/何时触发）→
  `temporal[]`；
- 与 `DATE` 实体分界：`DATE` 是**实体**（2017年7月1日）出现在图中作为节点/字面量；
  `temporal` 是**把时间语义绑定到某主体**（"该指引自该日起实施"）。DATE 回答
  "什么时间"，temporal 回答"何时生效/多频繁/什么窗口"。
- `value` 含绝对日期时，`anchor` 指向对应 DATE 实体，形成关联。

### 2.5 actions[]（动作处置）

```
actions: [{
  name,              # 动作名（如「书面风险警示」「暂停销售」）
  actor?,            # 执行者（实体 canonical，可空）
  level,             # 动作级别，独立 3 类枚举
  target?,           # 作用对象（实体 canonical，可空）
  side_effect?,      # 副作用/代价（可空，逐字或贴近原文）
  trigger?,          # 触发情形（可空，常与 rules 的 condition 呼应）
  evidence
}]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `level` | 动作级别，独立 3 类枚举 | `OBSERVE WARN INTERVENE`；判不出用 `OBSERVE`，不自创类型 |
| `side_effect` | 副作用/代价 | 可空；对齐 ActionType 的 side-effects（"会产生什么副作用"） |
| `trigger` | 触发情形 | 可空；常对应 `rules.condition` |

**level 枚举（动作级别，独立 3 类，对齐文章预测输出五项之"建议动作级别"）**：
| 枚举值 | 含义 | 示例 |
|---|---|---|
| `OBSERVE` | 观察/记录 | 记录、监测、留痕、保存 |
| `WARN` | 警示/提示 | 书面风险警示、提示告知、签署确认 |
| `INTERVENE` | 干预/处置 | 暂停销售、强制平仓、拒绝交易、上报 |

**分界原则**：
- 文本给出**处置动作 + 级别/代价**（警示、暂停、上报、拦截 + 造成什么后果）→
  `actions[]`；
- 与 `rules` 分界：`rules` 是条件-动作**规范**（应当/不得做什么，道义模态）；
  `actions` 是**处置动作的元信息**（动作本身 + 级别 + 副作用 + 触发情形）。
  同一句可同时产出 rule（应当进行特别书面风险警示）与 action（警示，级别 WARN，
  副作用=投资者需签署确认）。二者互补不重复迁移。

### 2.6 constraints[]（约束）与 permissions[]（权限）

```
constraints: [{
  subject,           # 约束对象（实体 canonical）
  type,              # 约束类型，独立 6 类枚举
  description,       # 约束内容（逐字/贴近原文）
  evidence
}]
permissions: [{
  actor,             # 执行者/角色（实体 canonical）
  action,            # 动作名（允许/禁止的动作）
  effect,            # 效果，独立 2 类枚举
  scope?,            # 范围/条件（可空）
  evidence
}]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `constraints[].type` | 约束类型，独立 6 类枚举 | `CARDINALITY VALUE_RANGE ENUM DISJOINT REQUIRED CONSISTENCY`；判不出用 `CONSISTENCY` |
| `permissions[].effect` | 授权效果，独立 2 类枚举 | `PERMIT DENY`；判不出用 `DENY`（默认禁止） |

**constraints.type 枚举（约束类型，独立 6 类，对齐 SHACL 约束组件）**：
| 枚举值 | 含义 | SHACL 对应 | 中文线索 |
|---|---|---|---|
| `CARDINALITY` | 基数约束 | sh:minCount/maxCount | 至少/至多/必须有一个；不少于…个 |
| `VALUE_RANGE` | 值域/取值区间 | sh:minInclusive 等 | 在…至…之间；不得低于/高于 |
| `ENUM` | 枚举取值 | sh:in | 只能为以下之一；分为…五级 |
| `DISJOINT` | 类不相交 | owl:disjointWith / sh:disjoint | 不得同时是…；互斥 |
| `REQUIRED` | 必填/必备 | sh:minCount≥1 | 应当具备/必须提供 |
| `CONSISTENCY` | 一致性/完整性 | SHACL 校验 | 前后一致；不得矛盾；完整性要求 |

**分界原则**：
- **约束**：文本对某对象给出**合法性/一致性要求**（必须具备/只能取值/不得矛盾/数量
  限制）→ `constraints[]`；与 `rules` 分界：`rules` 是"该做什么"的**规范**（道义
  模态），`constraints` 是"什么合法"的**结构约束**（SHACL 式，供数据校验）。
- **权限**：文本明确**谁能（不能）执行某动作**（授权/禁止/审批权）→ `permissions[]`；
  与 `rules` 分界：`rules` 的 PROHIBITION 是业务禁令（不得销售不匹配产品），
  `permissions` 是**主体-动作授权边界**（仅特定角色可执行）。业务禁令进 rules，
  授权边界进 permissions，LLM 语义判定。

## 4. 与五件套的衔接（分界总表）

| | relations[] | attributes[] | rules[] | processes[] | **states[]** | **functions[]** | **temporal[]** | **actions[]** | **constraints[]** | **permissions[]** |
|---|---|---|---|---|---|---|---|---|---|---|
| 语义 | 实体间事实 | 字面量属性 | 条件-动作规范 | 活动+控制流 | **对象状态演化** | **指标计算定义** | **时间语义绑定** | **处置动作+级别/副作用** | **结构合法性约束** | **主体-动作授权** |
| 句式 | 主语-谓词-宾语 | 实体.属性=值 | 应当/不得/可以 | 先…再…最后 | **处于…状态/由…转为…** | **=由…计算/综合…得出** | **自…起/每年/未来…** | **警示/暂停/上报…** | **必须/只能/至少…** | **仅…可…/禁止…执行** |
| 判定线索 | 宾语是实体 | 宾语是字面量 | 道义动词/条件-动作 | 顺序/阶段/流程 | **对象生命周期/状态迁移** | **指标定义式** | **时态限定语** | **处置动作+级别/代价** | **SHACL 式结构约束** | **授权/禁止主体-动作** |
| 入图 | 加边 | 加字面量边 | 不入图 | 不入图 | **不入图** | **不入图** | **不入图** | **不入图** | **不入图** | **不入图** |

> **最易混淆的 4 组分界（写进提示词）**：
> 1. `processes` vs `states`：活动序列 vs 对象生命周期（怎么走 vs 怎么变）。
> 2. `rules` vs `actions`：规范义务（该不该做）vs 处置元信息（怎么做/什么级别/代价）。
> 3. `rules` vs `constraints`：业务规范（应当）vs 结构约束（合法/必填/取值）。
> 4. `attributes` vs `functions`：字面量值 vs 计算定义（当前值 vs 定义式）。
> 五件套 + 六件套**并行不互斥**：同一句可同时产出多件套（如"应当进行特别书面风险
> 警示"→ rule + action；"普通投资者申请转化为专业投资者"→ relation + process + states）。

## 6. 决策点（建议默认值，待确认）

| # | 决策点 | 建议默认值 | 理由 |
|---|---|---|---|
| ① | 六类是否全部实现，还是分期 | **分期**：P0 先做 `states`（预测引擎）+ `functions`（机理）；P1 做 `temporal` + `actions`；P2 做 `constraints` + `permissions` + relations 增强 | 与决策链路对齐（先能预测，再能决策，最后治理）；每期独立可验证 |
| ② | `states` 的迁移表示 | `states[]`（label/initial）+ `transitions[]`（from/to 整数下标 + event/condition/action） | 对齐 SCXML/UML 状态机语义；下标引用 + 越界丢弃复用 flows 的惰性锚点模式 |
| ③ | `functions` 的 formula 表示 | LLM 声明式自然语言/运算符描述，**不强制可执行数学表达式** | 契约即规则：LLM 语义交卷，Python 不解析公式；公式是否可执行化是下游消费层的事 |
| ④ | 六类是否入图 | **均不入实体-边图**，独立产出 + metadata 计数；仅 relations 的 prop_kind/strength 作为边属性入图 | 与 rules/processes 哲学一致；预测/决策是消费层基于图 + 独立产出的推理，不强塞进实体边图 |
| ⑤ | `constraints` 与 `permissions` 分列还是合并 | **分列**两个数组，枚举各自独立 | SHACL（结构约束）与 RBAC（授权）语义不同，合并会污染枚举；渲染与校验各自独立 |
| ⑥ | relations 传导增强是否本期做 | 本期**只扩展契约字段**（prop_kind/strength + schema + 透传），不做图传播计算 | 图传播（GNN/衰减）是消费层算法，非抽取职责；先让 LLM 产出传导语义标注 |
| ⑦ | 渲染器新增 Tab 数量 | 新增 6 个 Tab（状态机/指标函数/时态/动作处置/约束/权限），关系 Tab 加 2 列 | 每类独立可读；状态机用确定性 SVG（对齐现有流程 Tab 渲染器） |
