# smini-extract 业务流程抽取设计方案（提案 v1）

> 状态：**已认可已实现**（用户确认 6 决策点后落地；对应 `smini` v4 五件套，
> 9 个流程用例 + 全量回归 130 全绿，端到端验证留档 `runs/verify-processes/`）。
> 目标：在「实体-关系三元组 + 实体属性 + 业务规则」之上，显式抽取**业务流程**
> （步骤 + 控制流），与现有链路无缝衔接，延续「契约即规则」哲学
> （LLM 全权语义 + Python 惰性锚点）。
> 用户偏好：契约即规则（Rule-by-Contract），尽量用声明式规则让大模型实现，
> 尽量少用确定性的 Python 实现。

---

## 0. 设计立场（延续契约即规则）

- **业务流程抽取不是新增流程引擎**，而是把 LLM 已能识别的「有序活动 + 控制流」
  结构**显式化、契约化**。
- LLM 一次交卷（第五件套 `processes[]`）；Python 只做确定性映射 + 惰性锚点
  （ID / 下标校验 / 统计），不判断流程语义、不拓扑校验。
- 不破坏现有契约与 121 个测试：旧 `relations` / `attributes` / `rules` 继续兼容
  （五件套并存）。

## 1. 本体论业务流程调研结论（资料来源见文末）

### 1.1 过程本体的表示：PSL / DOLCE / BPMN 元模型

- **PSL（Process Specification Language，ISO 18629）**：过程本体顶层由
  `Activity`（活动类型）、`activity-occurrence`（活动发生实例）、`timepoint`
  （时间点）、`object`（对象）构成。核心是**活动**——流程的最小执行单元。
- **DOLCE**：区分 `endurant`（独立体/对象，如投资者）与 `perdurant`（持续体/
  过程/事件，在时间中延展）。**流程在时间中延展，是一类特殊实体**，区别于
  OWL 中的静态个体。这是"流程成为本体第五类抽取对象"的本体论依据。
- **BPMN 元模型**（Automatic Generation of Ontologies from BPM）：Process /
  Activity / SubProcess / Event / Gateway / Actor / Artifact 三大类 19 个类。
  流程 = 活动 + 事件 + 网关（决策点）+ 参与者 + 数据对象，靠**序列流**连接。

### 1.2 控制流模式（Workflow Patterns，van der Aalst 基本控制模式）

流程的结构骨架由有限的**控制流模式**构成，文本中的顺序词（首先/然后/最后）、
分支词（如果…否则…）、并行词（同时/同步）、循环词（重复/直到）对应：

| 模式 | 类型 | 中文线索（给 LLM 的判定原则） |
|---|---|---|
| Sequence（顺序） | `SEQUENCE` | 先…再…然后…最后；依次；随后 |
| Parallel Split（并行分裂 AND） | `PARALLEL` | 同时；同步；一并；两个/多个并行 |
| Exclusive Choice（排他选择 XOR） | `CONDITIONAL` | 如果…则…否则…；当…时；分别 |
| Loop（循环） | `LOOP` | 重复；循环；直到；每次…都 |

> 合并（join）/同步（synchronization）不显式建模——分支汇合到下一公共步骤
> 时由 LLM 隐式表达，避免流程结构过度复杂（见决策点 ③）。

### 1.3 LLM 流程抽取研究（A Universal Prompting Strategy, arXiv 2407.18540）

该工作把流程信息抽取拆为三子任务，并验证 LLM 显著优于规则法（F1 高 8%）：
- **Mention Detection（MD）**：抽活动（activities/actions）、参与者（actors）、
  业务对象（business objects/data）。
- **Entity Resolution（ER）**：跨句指代消解（"it is examined" 的 it = 前面提到的
  claim）——同一活动/参与者多处提及要合并。
- **Relation Extraction（RE）**：三种关系——
  `performer`（参与者执行活动）、`uses`（活动使用数据对象）、`flow`（活动间的顺序）。

Prompt 结构三模块：**Context**（角色=流程建模专家 + 任务背景）+ **Task
Description**（元语言定义抽取元素类型 + CoT 分步）+ **Restrictions**（输出格式
约定 + 消歧提示 + few-shot 示例）。消融显示 CoT / 消歧提示 / reflection /
fact check list 均有正向作用。

**关键启示**：活动的三要素 = label（做什么）+ actor（谁做）+ data（用/产什么）；
活动间靠 flow 连接。这正是我们 `steps[]` + `flows[]` 设计的直接来源。

### 1.4 规则流视角（BPRF / Business as Rulesual, arXiv 2505.18542）

业务文档（银行/电商/医疗）的流程常**不靠显式动作序列**，而靠**互相依赖的规则**
表达：`<Condition, Action>` 对 + 三种依赖——`sequential`（一个规则完成后执行
下一个）、`conditional`（上一规则的取值决定走哪条分支）、`parallel`（多规则同时
执行）。识别方法为**两阶段**：先抽规则，再成对（pairwise）判断依赖。

**关键启示**：
- 我们已抽的 `rules[]`（condition+action+modality）本身就是流程的重要载体；
  `processes[]` 与其互补——流程聚焦"谁在何时按什么顺序做什么"，规则聚焦"条件满足
  时该不该做什么"。
- 控制流的三种依赖（sequential/conditional/parallel）与我们决策点 ③ 的
  `SEQUENCE / CONDITIONAL / PARALLEL` 一一对应，**共享同一套 LLM 判定语义**，
  只是表达对象不同（规则依赖 vs 步骤连接）。

## 2. 契约设计（第五件套 processes[]）

**宿主交卷新增 `processes[]`，仍不含偏移、不含 ID：**

```
processes: [{
  name,                # 流程名（规范名，LLM 判定，如「投资者适当性管理流程」）
  description,         # 可选：一句话说明流程目的
  steps: [             # 步骤（活动/事件/决策点），按执行顺序排列
    { label, kind, actor, evidence }
  ],
  flows: [             # 控制流（连接步骤）
    { from, to, type, condition, evidence }
  ]
}]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `name` | 流程名 | 规范名，同一流程跨文档一致 |
| `steps[].label` | 步骤内容（做什么） | **逐字/贴近原文** |
| `steps[].kind` | 步骤类型，独立 3 类枚举 | `TASK EVENT GATEWAY`；判不出用 `TASK` |
| `steps[].actor` | 执行者/参与者 | 用实体 `canonical`；**可空**（被动/隐式） |
| `flows[].from/to` | 步骤引用 | **整数下标**（指向 `steps` 数组，0-based） |
| `flows[].type` | 控制流类型，独立 4 类枚举 | `SEQUENCE PARALLEL CONDITIONAL LOOP`；判不出用 `SEQUENCE` |
| `flows[].condition` | 分支条件 | 仅 `CONDITIONAL` 用；其余可空 |
| `evidence`（step/flow） | 原文短引用 | **逐字取自原文**，用于溯源 |

**kind 枚举（步骤类型，独立 3 类）**：
| 枚举值 | 含义 | 中文线索 |
|---|---|---|
| `TASK` | 活动/任务 | 填表、评估、签署、回访（动词性动作） |
| `GATEWAY` | 决策/分支点 | 判定、选择、匹配、若…则分两路 |
| `EVENT` | 事件 | 开始/结束/触发（如"收到申请时"）；判不出不抽 |

**flow.type 枚举（控制流类型，独立 4 类，对齐 Workflow Patterns 基本控制模式）**：
| 枚举值 | 含义 | 中文线索 |
|---|---|---|
| `SEQUENCE` | 顺序 | 先…再…然后…最后；依次 |
| `PARALLEL` | 并行（AND-split） | 同时；同步；一并 |
| `CONDITIONAL` | 排他分支（XOR-split） | 如果…则…否则…；当…时 |
| `LOOP` | 循环 | 重复；直到；每次…都 |

> **分界原则（写进提示词，无代码规则）**：
> 文本含**顺序/阶段/流程性描述**（顺序词、阶段词、「流程」「步骤」「先…再…
> 最后」、生命周期）→ 抽 `processes[]`；纯事实陈述（relations/attributes）、
> 纯规范约束（rules）不因流程抽取而重复。五件套并行不互斥——同一句
> 「证券经营机构对投资者进行综合评估」可同时是 relation、也是流程 step，
> 由 LLM 判定其在流程中的位置。

## 3. 惰性锚点（消费层 build_kg 兜底，不用 LLM 操心）

| 锚点 | 规则 | 位置 |
|---|---|---|
| process_id | `sha256(name)` 内容寻址，跨进程幂等 | `smini/ids.py` |
| step_id | `sha256(process_id, 下标, label)` 内容寻址 | `smini/ids.py` |
| flow 下标 | `from/to` 越界（<0 或 ≥len(steps)）→ **丢弃该 flow** + 降级登记 | 薄壳 |
| 流程入图 | **不入实体-边图**（流程是 perdurant/持续体，非实体间事实）；`metadata.process_count` 登记 | `build_kg.py` |
| 去重 | 同 name 即同流程，按 process_id 合并 | 薄壳 |

## 4. 与四件套的衔接（分界，核心）

| | 关系 `relations[]` | 属性 `attributes[]` | 规则 `rules[]` | **流程 `processes[]`** |
|---|---|---|---|---|
| 语义 | 实体间事实 | 实体字面量属性 | 条件-动作/规范 | **有序活动 + 控制流（在时间中延展）** |
| 句式 | 主语-谓词-宾语 | 实体.属性=值 | 应当/不得/可以… | **先…再…最后 / 如果…则… / 同时…** |
| 判定线索 | 宾语是实体 | 宾语是字面量 | 道义动词/条件-动作 | **顺序/阶段/流程性描述** |
| 入图 | 加边 | 加字面量边 | 独立产出（不入图） | **独立产出（不入图）** |

> **流程与规则最易混淆**：规则是「条件→动作」的**规范**（该不该做、被约束）；
> 流程是「谁→按什么顺序→做什么」的**执行结构**（怎么走）。同一文本可两者
> 兼有——监管指引里「证券经营机构应当向投资者充分披露信息」（rule）与
> 「填表→评估→定级→匹配→签署→回访」（process）是正交的。

  签署→回访）留档 `runs/verify-processes/`。

## 6. 决策点（建议默认值，待确认）

| # | 决策点 | 建议默认值 | 理由 |
|---|---|---|---|
| ① | 流程表示结构 | `steps[]`（label/kind/actor）+ `flows[]`（from/to/type/condition）单列表 | 对齐 PSL/BPMN 语义但避免多类分裂复杂度，LLM 易交卷 |
| ② | 流程是否入图 | **不入实体-边图**，独立产出 + metadata.process_count | 与 rules 一致；流程是 perdurant 不是实体间事实 |
| ③ | 控制流类型 | 4 类 `SEQUENCE / PARALLEL / CONDITIONAL / LOOP`；合并不显式建模 | Workflow Patterns 基本控制模式精简，够用且防过度复杂 |
| ④ | steps 的 actor | 用实体 `canonical`，不强建新实体；引不到可空 | 与 attributes 归属同哲学，不增加图谱负担 |
| ⑤ | flows 的 from/to | **整数下标**引用 steps；越界丢弃并降级登记 | LLM 无法引用 Python 补算的 id，下标最稳；惰性校验 |
| ⑥ | 渲染 | 新增流程清单 Tab：确定性 SVG 线性流程图 + 分支标注 + 步骤/控制流表 | 流程天然适合图表达，不增加外部依赖 |
