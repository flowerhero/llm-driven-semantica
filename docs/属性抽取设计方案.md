# smini-extract 属性抽取设计方案（提案 v1）

> 状态：**待用户认可**，认可后再实现。
> 目标：在现有「实体-关系三元组」契约之上，显式抽取**实体属性**（本体论 DatatypeProperty），
> 与现有链路无缝衔接，延续「契约即规则」哲学（LLM 全权语义 + Python 惰性锚点）。

---

## 0. 设计立场（延续契约即规则）

- **属性抽取不是新增规则引擎**，而是把 LLM 已能做的事**显式化、契约化**。
- LLM 仍是一次交卷；Python 只做确定性映射 + 惰性锚点，不判断语义。
- 不破坏现有契约与 107 个测试：旧 `relations` 字面量宾语继续兼容（双轨并存）。

---

## 1. 本体属性抽取规则调研结论（资料来源见文末）

### 1.1 OWL 属性三分法（W3C OWL 2）

| 属性类型 | OWL 关键词 | 连接对象 | 判定依据 | 本方案对应 |
|---|---|---|---|---|
| 对象属性 | `owl:ObjectProperty` | 个体 → 个体 | range 是**类** | 现有 `relations`（不变） |
| 数据属性 | `owl:DatatypeProperty` | 个体 → 字面量 | range 是**字面量**（xsd 类型） | **新增 `attributes`（本次核心）** |
| 注解属性 | `owl:AnnotationProperty` | 任意 → 字符串 | 元数据标注 | 暂不建模（工程上无抽取价值） |

> **核心判定规则**：看宾语的取值范围 —— 是「可独立成实体的对象」→ 关系；
> 是「数字/日期/字符串/量」→ 属性。这是写进提示词的唯一分界原则。

### 1.2 属性抽取的方法谱系（知识图谱综述）

| 方法 | 说明 | 本方案取舍 |
|---|---|---|
| 规则/模式 | 手工定义模式（如数词+量词触发、属性词扫描） | ❌ 确定性规则已整体删除，不回归 |
| 半结构化 | 百科信息盒、网页表格、垂直网站包装器 | ❌ 输入是归一化纯文本，不适用 |
| ML/DL | 特征向量、BERT/RNN 槽位填充 | ❌ 无训练数据，与零规则架构冲突 |
| **LLM 引导** | 预定义属性列表 + 允许识别新属性 | ✅ **采用**：ExtractGPT / Amazon 实践 |

### 1.3 属性建模三分（标准本体方法）

- **基础属性**：唯一、稳定（如标准编号、名称、成立日期）
- **业务属性**：业务特征（如注册资本、经营范围、风险等级）
- **约束属性**：约束条件（如有效期、适用范围、限额）

> 本方案不强制 LLM 区分这三类（避免过度设计），但 `value_type` 与属性名归一化
> 规则吸收其思想。

### 1.4 LLM 属性抽取实践要点（ExtractGPT / Amazon / Google structured output）

1. 用 **JSON Schema 约束输出结构**（本方案沿用 `EXTRACT_SCHEMA` 机制）
2. **预定义属性表 + 允许新增**：给常用属性名做提示词示例，但不封闭枚举
3. 属性值抽取 = **槽位填充**：属性名作为"问题"，文本中找答案
4. 未知值标 `n/a` 而非编造 —— 与本项目「不造假必须出声」一致

## 2. 契约扩展（宿主交卷：两件套 → 三件套）

```
entities:   [{ surface, canonical, type }]                              # 不变
relations:  [{ subject, predicate, object, object_type, evidence }]     # 不变（兼容字面量宾语）
attributes: [{ entity, name, value, value_type, evidence }]             # ★ 新增
```

### 2.1 attribute 条目结构

```json
{
  "entity": "证券经营机构",
  "name": "成立日期",
  "value": "2017年7月1日",
  "value_type": "DATE",
  "evidence": "自2017年7月1日起实施"
}
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `entity` | 属性所属实体（canonical） | 必须能在 `entities[]` 中匹配到 |
| `name` | 属性名（归一化语义词） | 不用句子片段；同义归一（成立日期/成立于 → 成立日期） |
| `value` | 属性值 | **逐字取自原文** |
| `value_type` | 属性值类型（独立枚举） | 见 §3 |
| `evidence` | 支撑原文短引用 | 逐字取自原文，用于溯源 |

> **关键决策**：`value` 是字面量，**不给 ID、不给 canonical、不给 type**——
> 它不指向实体，只挂数据。这让 LLM 的判断职责清晰：宾语是实体 → relations，
> 宾语是字面量 → attributes。

---

## 3. value_type 独立枚举（字面量值类型）

> 不复用 `EntityType`（那是实体的类型）；属性值只有字面量，用独立枚举。

| value_type | 判定依据 | 例 |
|---|---|---|
| `DATE` | 日期/年份表达 | 2017年7月1日 |
| `TIME` | 时刻表达 | 15:30 |
| `MONEY` | 金额 + 币种/单位 | 1亿元 |
| `PERCENT` | 百分比 | 30% |
| `QUANTITY` | 数字 + 量词 | 5吨、10公里 |
| `NUMBER` | 纯数字（无单位） | 3家 |
| `BOOLEAN` | 是/否、有/无、真/假 | 是 |
| `ENUM` | 枚举值（高/中/低、合格/不合格） | 高风险 |
| `STRING` | 普通字符串 | 上海市浦东新区 |
| `OTHER` | 逃生口：判不出用它，不自创 | — |

## 4. 属性抽取规则（写进提示词的原则，非代码）

> 延续零规则哲学：这些是给 LLM 的**判定原则**，不是可执行规则。

1. **值域分界**（唯一硬分界）：宾语是独立实体 → `relations`；宾语是字面量 → `attributes`。
2. **属性名归一**：用语义概括词做属性名（如「成立日期」「注册资本」「风险等级」），
   不用句子片段；同一属性跨文档用同一 `name`。
3. **值逐字**：`value` 必须逐字取自原文，不改写、不转述、不概括。
4. **类型判定**：由值的形式判 `value_type`（见 §3 表）。
5. **只抽事实性属性**：抽实体固有/静态特征（基础+业务+约束属性），不抽观点、建议、口号。
6. **多值允许**：同一 (entity, name) 可有多条，交 QA 冲突机制裁决或保留。

---

## 5. 惰性锚点（Python 兜底，LLM 不参与）

| 锚点 | 规则 | 位置 |
|---|---|---|
| attribute_id | `sha256(entity, name, value)` 内容寻址，跨进程幂等 | `smini/ids.py` 新增 |
| value span | 对 `value` 尽力 `find`，找不到给 -1 | 薄壳 |
| evidence span | 尽力定位，找不到 null | 薄壳 |
| value_type 校验 | 不在枚举 → `OTHER`（Python 兜底修正） | 薄壳 + validate |
| entity 匹配 | `entity` 匹配不到 `entities[]` → 降级为关系宾语（`OTHER` 实体） | 薄壳 |

## 6. 消费层接入（build_kg / QA / 渲染）

### 6.1 薄壳映射（extract.py）

`attribute → Triplet`：`subject=entity, predicate=name, object=value, object_type=value_type, object_literal=True`
—— 直接复用现有 Triplet 链路，`extractor="llm.attr.v1"` 标记来源。

### 6.2 build_kg.py

- attribute 三元组 → `KGEdge`（`object_literal=value`），事实级溯源保留（边带双时态/evidence）
- **同时** `Entity.properties[name] = value` 聚合视图（建图时同步写入），
  复用 `merge_with` 已有的属性冲突合并策略（KEEP_MOST_COMPLETE / UNION_PROPERTIES）

### 6.3 QA（冲突检测）

- 同一 (entity, name) 多值 → `ConflictKind.VALUE` 冲突 → 复用 majority_vote / keep_all 裁决

### 6.4 渲染（render_viewer.py）

- 新增「属性清单」区块：实体 → 属性名 → value / value_type / evidence 表格

## 8. 待确认决策点

1. **双轨 vs 收敛**：新增 `attributes` 显式通道后，`relations` 的字面量宾语是
   **保留兼容**（建议）还是强制迁到 `attributes`？（建议保留，不破坏旧契约）
2. **属性落位**：属性同时写 `Entity.properties` 和字面量 `KGEdge`（建议，兼顾聚合与溯源），
   还是只写其一？
3. **value_type 枚举**：是否按 §3 的 10 类，还是精简为
   `DATE/MONEY/PERCENT/QUANTITY/STRING/OTHER` 6 类？（建议 10 类，覆盖 ENUM/BOOLEAN/NUMBER 常见场景）
4. **是否允许跨实体属性**（如"证券经营机构的注册资本"同时挂多个实体）？
   （建议允许，属性可多挂，交 QA 处理）
