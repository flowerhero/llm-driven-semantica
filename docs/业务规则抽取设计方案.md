## 0. 设计立场（延续契约即规则）

- **业务规则抽取不是新增规则引擎**，而是把 LLM 已能识别的「条件-动作/结论」
  结构**显式化、契约化**。
- LLM 仍是一次交卷；Python 只做确定性映射 + 惰性锚点，不判断规则语义。
- 不破坏现有契约与 113 个测试：旧 `relations` / `attributes` 继续兼容
  （四件套并存）。

## 1. 本体论业务规则调研结论（资料来源见文末）

### 1.1 本体规则的标准表达：SWRL（Horn 子句）

W3C SWRL（Semantic Web Rule Language）把规则表示为 **Body（前提/IF）→
Head（结论/THEN）** 的 Horn 子句，用 OWL 原子（类/属性断言）连接。它是
本体「描述层（OWL）」与「规则推理层」的桥梁——本体定义概念/属性/关系，
规则负责「条件-结论」的逻辑推导。这是本体业务规则的**标准骨架**。

> 一条 SWRL 规则 = `前提(Body/IF) ⇒ 结论(Head/THEN)`。
> 我们的 `rules[]` 契约即对应这个 IF-THEN 骨架。

### 1.2 业务规则的经典分类（业务规则工程）

业界对业务规则有一致的三/四大类划分（TAW01、Sparkling Logic、MBA 智库）：

| 类型 | 英文 | 特征 | 对应 SWRL 形态 |
|---|---|---|---|
| **约束规则** | Integrity/Constraint | 检查状态是否合规（字段格式、枚举范围、必填） | 条件 + 约束断言 |
| **派生规则** | Derivation/Calculation | 由已知值推导新值（IF-THEN 产生式） | Body ⇒ Head 纯推导 |
| **反应规则** | Reaction/Stimulus-Response | 事件触发动作（event-action） | 触发条件 ⇒ 动作 |
| **道义指派** | Deontological Assignment | 赋予角色**权利与义务**（应当/不得/可以） | 主体 ⇒ 模态+动作 |

> 前三类本质是「条件→结论」；第四类（道义指派）加了一层**模态**——
> 这正是法律/监管文本（如证券适当性指引）最核心的规则形态。

### 1.3 道义逻辑四模态（法律规范基本模态）

法律/监管规则的道义（Deontic）语义，学界一致归纳为四种基本模态
（ACM CFR 形式化框架、熊静波「法律最小公分母」）：

| 模态 | 中文表达 | 典型动词 |
|---|---|---|
| **义务** Obligation | 必须做 | 应当 / 必须 / 应 / 须 |
| **禁止** Prohibition | 不得做 | 不得 / 禁止 / 严禁 / 不可 |
| **许可** Permission | 可以做 | 可以 / 有权 / 允许 / 可 |
| **豁免** Dispensation | 可不做（非强制） | 可不 / 豁免 / 无需 |

> 另有「条件派生（非道义）」形态：无模态词的纯 IF-THEN 推导（如
> 「风险承受能力等级由低到高划分为 C1-C5」→「等级越高可承受风险越大」）。
> 我们用独立的 `CONDITIONAL` 类型承载，避免强行塞进道义四模态。

### 1.4 法律规则的 4-tuple 结构（Governatori & Rotolo）

监管规则的形式化主流结构是四元组：`r = ⟨S 主体, Θ 条件, Π 约束, κ 上下文⟩`。
义务/禁止/许可等 actor-CU（Compliance Unit）都面向**承担角色的主体**。
这给了我们 `rules[]` 的字段骨架：**主体 + 条件 + 模态 + 动作/结论**。

### 1.5 LLM 规则抽取的成熟做法（2024-2026 前沿）

| 方法/论文 | 核心做法 | 对我们的启示 |
|---|---|---|
| De Jure（迭代自精炼） | schema 驱动，规则单元拆 9 字段：action / action object / method / conditions / constraints / exceptions / penalties / purpose / verbatim span；**抑制非规则段落**（前言/定义/交叉引用表）防规则集膨胀 | 抑制噪声：定义、标题、序言不进规则 |
| Executable Governance | 每条规则带 provenance（source.doc / citation / span_id）+ scope / hazard / conditions / exceptions / requirements / severity | 规则必须可溯源（evidence 逐字） |
| PolicyKG（道义中间表示） | 条款挖掘：检测**道义标记**（应当/不得）、例外线索（unless）、主体提及、数量/时间指标、交叉引用 | 抽取触发线索 = 道义动词 + 条件词 + 例外词 |
| From Legal Texts to DDL | 规则改写为规范形式后映射：may→PERMISSION、shall not→FORBIDDEN、must→OBLIGATION；**前件原子不得出现在后件** | 模态由道义动词映射；结构约束给 LLM |
| 证券规则规约（元模型法） | 定义 15 类实体 + key/value 处理低频约束 | 规则可关联到实体契约 |
| BREX 基准 | 409 业务文档 / 2855 条专家标注规则 / 30+ 领域 | 规则抽取有真实基准，验证可行性 |

### 1.6 与现有三件套的分界（关键设计点）

| | 关系 `relations[]` | 属性 `attributes[]` | **规则 `rules[]`（新）** |
|---|---|---|---|
| 语义 | 实体间事实（ObjectProperty） | 实体字面量属性（DatatypeProperty） | **条件-动作/结论（规范/推导）** |
| 句式 | 主语-谓词-宾语（陈述） | 实体.属性=值（陈述） | **如果…则… / 应当… / 不得… / 可以…** |
| 判定线索 | 宾语是实体 | 宾语是字面量 | **道义动词或条件-动作结构** |
| 是否可证伪 | 描述"是什么" | 描述"是什么" | 规范"应如何 / 什么条件下如何" |

> **核心分界原则（写进提示词，无代码规则）**：
> 含**道义模态词**（应当/必须/不得/禁止/可以/有权）或**条件-动作结构**
> （如果/当…时…则…）→ 进 `rules[]`；纯事实陈述 → 保持 `relations`/`attributes`。
> 同一句既含事实又含规范时（如「证券经营机构应当向投资者销售产品前
> 进行风险评估」），规范句进 `rules[]`，其中的实体关系仍可并行进
> `relations[]`（四件套并行，不互斥）。

## 2. 契约设计：rules[] 第四件套

**宿主交卷四件套，不含偏移、不含 ID：**

```
entities:   [{ surface, canonical, type }]
relations:  [{ subject, predicate, object, object_type, evidence }]
attributes: [{ entity, name, value, value_type, evidence }]
rules:      [{ subject, condition, action, modality, evidence }]
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `subject` | 规则主体（谁承担义务/被约束者） | 用实体 `canonical`；**可空**（纯派生/全局规则） |
| `condition` | 触发条件（前件/IF） | **可空**（无条件义务：直接"应当…"） |
| `action` | 动作/结论（后件/THEN） | **必有**，动作或结论的规范文本 |
| `modality` | 规则模态（独立枚举） | `OBLIGATION PROHIBITION PERMISSION CONDITIONAL OTHER`；判不出用 `OTHER` |
| `evidence` | 支撑本规则的原文短引用 | **逐字取自原文**，用于溯源 |

**modality 独立 5 类枚举**（不复用 EntityType / AttributeValueType）：

| 枚举值 | 含义 | 中文触发词（给 LLM 的判定原则） |
|---|---|---|
| `OBLIGATION` | 义务 | 应当 / 必须 / 应 / 须 |
| `PROHIBITION` | 禁止 | 不得 / 禁止 / 严禁 / 不可 |
| `PERMISSION` | 许可 | 可以 / 有权 / 允许 / 可 |
| `CONDITIONAL` | 条件派生（非道义） | 如果/当…时…则…，无模态词 |
| `OTHER` | 其他 | **逃生口**：判不出就用它，不自创类型 |

## 3. 惰性锚点（Python 确定性兜底，不用 LLM 操心）

| 锚点 | 规则 | 位置 |
|---|---|---|
| rule_id | `sha256(subject, condition, action, modality)` 内容寻址，跨进程幂等 | `smini/ids.py` |
| evidence span | evidence 尽力 `find`，找不到为 None | 薄壳 |
| modality | 非法 → `OTHER` 兜底，不自创 | 薄壳 |
| 去重 | 同 (subject, condition, action, modality) 即同规则，按 rule_id 合并 | 薄壳 + 消费层 |

> 与属性抽取一致：**不新增确定性规则函数**，rule_id 直接复用
> `stable_id("rule", subject, condition, action, modality)` 内容寻址，
> 不引入无消费者的 Python 逻辑。

## 4. 消费层接缝（最小化，延续"少 Python"）

**设计决策：规则不进入实体-边图谱（KGEdge），作为 ExtractionResult 的
独立产出 `rules[]` 保留。**

理由：
- 规则是「条件-动作/结论」结构，不是实体间事实——硬塞进实体-边图会
  污染图谱语义（KGEdge 只有 subject-predicate-object 三元形态，装不下
  condition + modality）。
- 规则的可执行语义（道义推理、冲突检测）是下游推理引擎（如 DDL 求解器、
  合规引擎）的职责，不是建图层。
- 对齐学界共识（NyayaEngine：LLM 只做事实抽取，决策/规则由确定性引擎
  处理；De Jure：规则独立 schema 单元）。

落位方式：
- `ExtractionResult` 新增 `rules: list[Rule]` 字段 + `stats.rules` 计数。
- `build_kg.py` 不消费 rules，但在 `KnowledgeGraph.metadata` 登记
  `rule_count`（供编排层可见"这批文档含 N 条规则"）。
- `QA` v1 不做道义冲突裁决（同一动作既应当又禁止等），仅统计登记；
  冲突检测留待下游（可后续由 LLM 做规则一致性审查）。
- 规则与实体的关联：v1 靠 `evidence` 溯源（规则可反查原文），不强制
  把 rule.subject/action 链接到图谱节点（避免过度工程）。

## 5. 提示词抽取原则（写进 build_extract_prompt，声明式）

1. **判定**：含道义动词（应当/必须/不得/禁止/可以/有权）或条件-动作结构
   （如果/当…时…则…）的句子 → 抽为 `rules[]`。
2. **结构**：`subject`（主体，可空）→ `condition`（条件，可空）→
   `action`（动作/结论，必有）→ `modality`（5 类枚举）→ `evidence`（原文短引用）。
3. **分界**：纯事实陈述（宾语是实体 → relations；宾语是字面量 →
   attributes）；规范/条件句 → rules。四件套并行不互斥。
4. **抑制噪声**：不抽定义、标题、序言、交叉引用表等非规则段落（防规则集
   膨胀——De Jure 做法）。
5. **不输出**偏移 / ID / 任何派生字段（Python 惰性锚点补算）。

## 7. 待用户决策点（建议方案已标注）

1. **规则结构**：5 字段（subject/condition/action/modality/evidence）是否足够？
   是否需要 `exception`（例外：除…外）或 `penalty`（罚则）字段？
   （建议：5 字段起步，`exception` 可作为可选第 6 字段，`penalty` 暂不——避免过度设计）

2. **规则是否入图**：规则作为独立产出（不入实体-边图，仅登记 rule_count）
   还是也建 Rule 节点入图？
   （建议：独立产出，v1 不入图——规则不是实体间事实，塞边会污染图谱语义）

3. **modality 枚举**：5 类（含 CONDITIONAL 覆盖纯推导）还是严格道义四模态
   （义务/禁止/许可/豁免）？
   （建议：5 类，CONDITIONAL 覆盖无模态词的 IF-THEN 派生，避免硬塞）

4. **规则冲突处理**：v1 是否做道义冲突检测（同一 action 既应当又禁止）？
   （建议：v1 只登记不裁决——冲突检测是下游 DDL 推理引擎的职责，且自动
   裁决易误判，交人工/LLM 一致性审查更稳妥）

5. **规则与实体关联**：是否把 rule.subject/action 与图谱实体节点硬链接？
   （建议：v1 靠 evidence 溯源，不强建链接——避免过度工程）
