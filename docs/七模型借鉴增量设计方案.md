## 一、借鉴原则

> **借字段语义，不借执行机制。**

对方七模型的价值不在其生成引擎（DDL / simpleeval / flow_engine / UI 生成——
与"读端"定位冲突），而在其揭示的建模维度。我方按"字段级增强 → 结构级增强 →
新通道（需确认）"三个层次借鉴，全部新增内容继续遵循：
LLM 语义判断 → 薄壳枚举校验 + 非法兜底 → evidence 溯源 → validate 可验证。

## 九、追加借鉴（2026-09-20 · 与 sharptoolbox v9 规范二次比对）

> 来源：`sharptoolbox/ontology_modeling_framework` README.md + ontology_modeling_framework_v9.md
> （作者 @人月聊IT，Apache-2.0）。v9 为单体同步版七模型（M1/M2/M3/M5/M6/M7/MU），
> 目标"建模→生成 IT 应用"；我方保持抽取定位，**只借字段语义与判定原则**，不借执行机制。

### 9.1 字段级追加：permissions.data_scope（借鉴 M5 Permission.dataScope）

v9 M5 的 `Permission.dataScope` 定义数据可见范围（ALL / OWN / DEPT / CUSTOM），
落到我方 `permissions` 通道：

| 借鉴来源 | 落点通道 | 新增字段 | 枚举 / 兜底 |
|---|---|---|---|
| M5 主体模型 | `permissions` | `data_scope`：数据可见范围（全机构 / 本人 / 本部门 / 自定义） | `DataScope`：ALL / OWN / DEPT / CUSTOM；非法→OTHER |

- **金融场景依据**：适当性留档、回访记录、权限审批中"仅本人可见 / 本部门可见 / 全机构可见"
  是真实数据隔离需求（监管留痕 + 最小权限）；
- **判定原则（写进提示词，无代码规则）**：文本出现"仅本人 / 本人名下""本部门 / 本单位范围
  内""全公司 / 全机构 / 全员可见"→ 分别填 `OWN` / `DEPT` / `ALL`；拿不准省略或 `OTHER`；
- **惰性锚点**：薄壳枚举校验兜底（非法→OTHER）；`data_scope` 不参与 `permission_id` 寻址；
  `render_viewer.py` 权限表增「数据范围」列。

### 9.2 判定原则追加：规则四层分级（借鉴 M1 内置字段 → refRules → invariants → M3 判定顺序）

v9 M3 用四层判断顺序决定规则归属（属性内置字段 → `Attribute.refRules` → `Aggregate.invariants`
→ M3 Rule）。翻译成我方抽取判定原则（**零字段变更，仅写进提示词**），
解决宿主把属性约束误抽成 `rules` 导致的规则集膨胀：

```
属性内置约束能表达（必填 / 唯一 / 枚举）？   → attributes.required / value_type=ENUM（不进 rules）
只依赖单个属性的扩展约束？                 → constraints（VALUE_RANGE / ENUM 等）
依赖同一对象多个属性 / 子实体的约束？        → constraints（CONSISTENCY）
跨对象 / 跨行为 / 需独立复用 / 含道义动词？   → rules（或 functions 承载计算定义）
```

| 原文特征 | 归属通道（新判定） | 反例（旧误抽） |
|---|---|---|
| "应当包含 XX 字段""必须填写" | `attributes.required=true` | 曾抽为 OBLIGATION 规则 |
| "至少划分为五级""不低于 10%"（单主体结构约束） | `constraints` | 曾抽为 CONDITIONAL 规则 |
| "投资者风险等级 ≥ 产品风险等级"（跨对象匹配） | `functions` 或 `rules`（含道义时） | — |
| "应当 / 不得 / 可以 …"（道义规范，真正该进 rules 的） | `rules` | — |

- **与现状关系**：不新增字段、不改变通道枚举；只把四层顺序并入
  `extraction-rules.md` §10（规则）与 §12.4（六件套）的判定原则，帮助宿主正确分通道。
