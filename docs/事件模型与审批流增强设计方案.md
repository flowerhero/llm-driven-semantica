## 0. 设计立场



* **契约即规则**：两个缺口全部由宿主 agent 按契约交卷（`events[]` 新件套 +

  `processes` 增字段），Python 只做确定性映射，不判断语义。

* **增量、不破坏**：既有十一件套（含五件套）契约原样保留；`events[]` 空数组合法；

  `processes` 新字段全部可选（缺省时行为与现状完全一致）。

* **不入图优先**：`events` 与审批流新字段均为独立产出 / 边属性，不新增实体 - 边语义。

* **ID 锚点键不变**：新字段不参与内容寻址，幂等保持。

## 设计一：events 通道（对齐 ME 事件模型）

### 1.1 本体论依据



* **事件 = 已发生 / 将发生的事实与状态变更记录**（文章 ME：业务事件、生产者 / 订阅者、

  事件链路），是 EDA（事件驱动架构）与 DDD 领域事件的本体对应。

* 与现有通道的本体分界：`processes` 是**执行结构**（谁→按什么顺序→做什么），

  `events` 是**事实与响应链**（发生了什么→谁响应）；`actions` 是**处置动作元信息**

  （怎么做 / 什么级别），事件是触发与承载。

* 对预测决策的价值：事件链把 "触发 → 响应 → 后续事件" 串成可推理的因果 / 触发网络，

  与 `states` 迁移、`rules` 触发互补（文章核心设计理念之一：事件解耦）。

### 1.2 契约格式（宿主交卷）



```
events: \[

&#x20; {

&#x20;   "name": "风险等级调整完成",

&#x20;   "trigger": "持续评估发现投资者风险承受能力变化",

&#x20;   "producer": "证券经营机构",

&#x20;   "subscribers": \["适当性管理岗", "交易系统"],

&#x20;   "payload": "投资者标识、原等级、新等级、调整时间",

&#x20;   "next\_events": \["适当性匹配重算"],

&#x20;   "kind": "STATE\_CHANGE",

&#x20;   "evidence": "根据更新的信息持续评估投资者风险承受能力，并及时调整其风险承受能力等级"

&#x20; }

]
```



| 字段            | 含义                   | 约束                                  |
| ------------- | -------------------- | ----------------------------------- |
| `name`        | 事件名（**内容寻址锚**）       | **必有**，短名如「订单已支付确认」                 |
| `trigger`     | 触发来源（自然语言）           | 可空；行为 / 流程步骤 / 条件 / 其他事件            |
| `producer`    | 生产者                  | 用实体 `canonical` 或系统名；可空             |
| `subscribers` | 订阅者列表                | 实体 canonical / 系统名数组；单字符串自动清洗成数组；可空 |
| `payload`     | 事件载荷（携带的数据）          | 自然语言描述；可空                           |
| `next_events` | 后续事件（事件链路）           | 引用其他事件 `name` 的数组；软校验；可空            |
| `kind`        | 事件类型（独立 5 类枚举，见 1.3） | 判不出用 `OTHER`，不自创类型                  |
| `evidence`    | 支撑本事件的原文短引用          | **逐字取自原文**，必有                       |

### 1.3 kind：独立 5 类枚举（不复用实体 / 规则 / 流程类型）



| 枚举值            | 含义          | 中文判定线索（给 LLM）         |
| -------------- | ----------- | --------------------- |
| `BUSINESS`     | 业务事实事件      | 成交 / 开户 / 审批通过 / 申请提交 |
| `STATE_CHANGE` | 状态变更事件      | 等级调整 / 状态由… 变为…/ 已激活  |
| `TIMER`        | 定时 / 到期事件   | 到期 / 到期日 / 定时 / 届满    |
| `EXTERNAL`     | 外部系统 / 环境事件 | 行情波动 / 监管通知 / 外部接口回调  |
| `OTHER`        | 其他          | **逃生口**：判不出就用它，不自创类型  |

### 1.4 判定原则（写进提示词，无代码规则）

> 出现
>
> **事件发布 - 订阅 - 链路**
>
> 语义（"… 后触发 / 通知 / 发布…"" 收到… 后执行…"
> "… 完成… 引起…"）→ 抽为 
>
> `events`
>
> 。
> 分界（并行不互斥，同一句可同时是事件与规则 / 流程步骤 / 状态迁移）：
> 与 
>
> `rules`
>
> ：rules 是 "应当 / 不得" 规范（条件→动作），events 是
>
> **已发生 / 将发生事实及响应链**
>
> （不含道义）；
> 与 
>
> `actions`
>
> ：actions 是
>
> **处置动作**
>
> （警示 / 暂停 / 惩戒，有 level），events 是
>
> **事实本身**
>
> （成交、到期、审批通过）；
> 与 
>
> `states`
>
> ：states 是状态拓扑（A→B 迁移），events 是
>
> **触发迁移的事实**
>
> ；
> 与 
>
> `processes`
>
> ：processes 是执行步骤序列，events 是
>
> **步骤 / 行为间的事实纽带**
>
> 。

### 1.5 惰性锚点



| 锚点                         | 规则                                                                                                         | 位置               |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------- |
| event\_id                  | `sha256(name, trigger, producer)` 内容寻址，跨进程幂等                                                               | `smini/ids.py`   |
| kind                       | 薄壳校验，非法 → `OTHER` 兜底                                                                                       | 薄壳               |
| subscribers / next\_events | 字符串数组清洗（单字符串自动转数组）                                                                                         | 薄壳               |
| 软引用                        | `subscribers` / `next_events` / `producer` 找不到实体引用 → **⚠ warning 不阻断**（与 `reused_by`/`sub_process_ref` 一致） | `smini validate` |
| 去重                         | 同 (name, trigger, producer) 即同事件，按 event\_id 合并                                                            | 薄壳               |
| 入图                         | **不入实体 - 边图**；`build_kg` metadata 登记 `event_count`                                                         | `build_kg.py`    |

## 设计二：processes 审批流增强（对齐 M6 的 APPROVAL 面）

### 2.1 现状与缺口

现状 `processes` 已有：`steps[]`（kind 6 类：TASK/GATEWAY/EVENT/START/END/SYSTEM\_TASK）、

`flows[]`（SEQUENCE/PARALLEL/CONDITIONAL/LOOP）、`sub_process_ref`（软引用）、

`preconditions/postconditions`。

缺口（对照文章 M6）：① 不区分**协同流 vs 审批流**；② 无**驳回 / 退回**；③ 无**角色泳道**；

④ 无**多级审批**的显式表达。

### 2.2 契约增强（全部可选，向后兼容）



```
processes: \[

&#x20; {

&#x20;   "name": "适当性匹配审批流程",

&#x20;   "flow\_type": "APPROVAL",

&#x20;   "approval\_chain": \["适当性管理岗", "合规审核岗", "业务负责人"],

&#x20;   "steps": \[

&#x20;     { "label": "初审", "kind": "TASK", "actor": "适当性管理岗", "lane": "运营部", "reject\_to": 0,

&#x20;       "evidence": "初审不通过的退回重新评估" },

&#x20;     { "label": "复核", "kind": "TASK", "actor": "合规审核岗", "lane": "合规部", "reject\_to": 0,

&#x20;       "evidence": "复核不通过的退回" },

&#x20;     { "label": "终审批准", "kind": "GATEWAY", "actor": "业务负责人", "lane": "业务部", "reject\_to": 1,

&#x20;       "evidence": "终审不通过退回复核" }

&#x20;   ],

&#x20;   "flows": \[

&#x20;     { "from": 0, "to": 1, "type": "SEQUENCE", "condition": "", "evidence": "" },

&#x20;     { "from": 1, "to": 2, "type": "SEQUENCE", "condition": "", "evidence": "" }

&#x20;   ]

&#x20; }

]
```



| 新增字段             | 位置        | 含义                     | 约束 / 兜底                                                              |
| ---------------- | --------- | ---------------------- | -------------------------------------------------------------------- |
| `flow_type`      | process 级 | 流程类型                   | `COLLABORATION`（端到端协同流，**默认**）/ `APPROVAL`（审批流）；非法 → `COLLABORATION` |
| `approval_chain` | process 级 | 审批链路摘要（角色 / 岗位名数组）     | 软引用；可空；多级审批以 steps 顺序为准，本字段为冗余摘要                                     |
| `lane`           | step 级    | 泳道（角色 / 部门名）           | 软引用字符串；可空                                                            |
| `reject_to`      | step 级    | 驳回目标（**整数下标**引用 steps） | 越界（<0 或 ≥len (steps)）→ **丢弃**；可空                                     |
| `on_reject`      | flow 级    | 驳回边条件（自然语言补充）          | 可空；与步骤级 `reject_to` 并存时**以步骤级为权威**                                   |

> **不新增&#x20;**
>
> `APPROVAL_TASK`
>
> **&#x20;kind**
>
> ：审批语义由 
>
> `flow_type=APPROVAL`
>
>  \+ 
>
> `reject_to`
>
>  \+ 
>
> `lane`
> 联合表达，避免 kind 枚举膨胀（kind 保持 6 类）。

### 2.3 判定原则（写进提示词，无代码规则）

> 含
>
> **审批 / 审核 / 复核 / 批准 / 会签**
>
> 语义 → process 标 
>
> `flow_type=APPROVAL`
>
> ；
> 纯业务流转（先… 再…）→ 不填（默认 COLLABORATION）。
> 出现 "
>
> **不通过 / 驳回 / 退回**
>
> " → 该步骤填 
>
> `reject_to`
>
> （回到哪个步骤的下标）；
> 出现 " 由 XX 部门 / 角色 / 岗
>
> **审核**
>
> " → 步骤填 
>
> `actor`
>
>  \+ 
>
> `lane`
>
> ；
> 多级审批 → 按
>
> **步骤顺序**
>
> 逐级表达（每级一个步骤），
>
> `approval_chain`
>
>  作冗余摘要（可选）。

### 2.4 惰性锚点



| 锚点                                | 规则                                                                                                                 | 位置                    |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------- |
| flow\_type                        | 薄壳校验，非法 / 缺失 → `COLLABORATION` 兜底                                                                                  | 薄壳                    |
| reject\_to                        | 越界（<0 或 ≥len (steps)）→ **丢弃该驳回**（LLM 下标不可信，与 flow 下标一致）                                                            | 薄壳                    |
| lane / approval\_chain            | 字符串数组清洗；软引用 → ⚠ warning 不阻断                                                                                        | 薄壳 / `smini validate` |
| process\_id / step\_id / flow\_id | **不变**（`sha256(name)` / `sha256(process_id,index,label)` / `sha256(process_id,from,to,type,condition)`）—— 新字段不参与寻址 | `smini/ids.py`        |
| 入图                                | 不入实体 - 边图；`build_kg` metadata 增 `approval_flow_count`                                                              | `build_kg.py`         |

### 2.5 审批结果三态（v1.1 增补 · 借鉴 sharptoolbox v9 M6 approvalOutcomes）

> 来源：`ontology_modeling_framework_v9.md` §6.3.3 `approvalOutcomes`（APPROVE / REJECT / RETURN）。
> 背景：初版用 `reject_to` 表达"不通过时回到哪"，但未区分**否决（流程终止）**与
> **退回（修改后重报）**——金融审批中两者处置不同（否决需重新提交申请；退回只需修改后重报），
> 须显式表达。

新增 step 级字段 `approval_outcome`（仅 `flow_type=APPROVAL` 的审批步骤使用；**可选，向后兼容**）：

| 枚举值 | 含义 | 判定线索（给 LLM） | 与 `reject_to` 的配合 |
|---|---|---|---|
| `APPROVE` | 通过 | "同意 / 批准 / 审核通过" | 无 `reject_to` |
| `REJECT` | 否决（流程终止） | "不予批准 / 否决 / 驳回申请" | 通常无 `reject_to`（流程终止）；如需回到起点重报可配 |
| `RETURN` | 退回（修改后重报） | "退回修改 / 退回重报 / 补正材料" | **必有** `reject_to`（回到修改步骤） |
| `OTHER` | 其他 | **逃生口**：判不出就用它，不自创类型 | — |

- **判定原则（写进提示词，无代码规则）**：审批步骤显式区分三态；"不通过"时先判断是
  **终止性否决**（REJECT）还是**可重报退回**（RETURN），再决定是否填 `reject_to`；
- **惰性锚点**：`approval_outcome` 薄壳枚举校验，非法 → `OTHER` 兜底；不参与 `step_id` 寻址；
  与 D6 兼容（不新增 `APPROVAL_TASK` kind，审批语义由 `flow_type + reject_to + lane + approval_outcome` 联合表达）；
- **渲染**：审批流步骤显示结果徽标（通过=绿 / 否决=红 / 退回=橙）；`reject_to` 回边沿用红色虚线。

## 6. 与现有能力的兼容性核对



* **向后兼容**：`events[]` 缺省空数组、processes 新字段缺省 —— 旧契约 / 旧产出无需任何改动即可通过校验。

* **幂等保持**：新字段不参与任何 ID 寻址；`process_id/step_id/flow_id` 键不变。

* **软引用哲学**：`subscribers/next_events/lane/approval_chain` 全部 ⚠ warning 不阻断，

  与 `reused_by/sub_process_ref/actor/role` 的宽松读端语义一致（区别于对方 "8 阶段硬暂停"）。

* **不入图**：events 独立产出，图谱仍保持 "实体间事实" 纯净语义。
