一、核心结论

两者是"本体工程"的一体两端，不是同一件事的两套做法。

  • 我方 smini-extract抽取（读）：把任意文本文档语义化为本体素材（实体-关系-属性-规则-流程 + 预测决策六件套），产出 JSON + 自包含 HTML 查看器。目标是"让文档成为可查询、可验证的知识图谱素材"。
  • 对方 ontology-driven-dev生成（建）：把业务需求经八阶段人工门禁确认成需求规格说明书，再建模为七模型 YAML（可执行规格），最终由内置 code-paas 底座生成可运行的全栈业务系统（Flask + SQLite + React，含流程引擎、权限、AI 对话框）。目标是"让需求变成系统"。
  • 共同点：都封装"本体驱动"方法论为 Skill；都由宿主 agent 充当 LLM（不依赖专用模型服务/API key）；都以结构化契约（JSON / YAML）作为"LLM 语义层"与"确定性代码层"的分界；都强调溯源与一致性验证。

关注面十一件套契约（JSON）七模型 YAML
对象/实体扁平实体表 {surface, canonical, type}，19 类封闭枚举（12 通用 + 7 金融扩展）M1 对象模型：DDD 聚合根/子实体、AggregateRootRef 外键、DictionaryRef 字典、生命周期状态、唯一约束

要点：对方模型的本质是"可执行规格"——每个模型都要能被确定性代码消费（建表、跑规则、走流程）；我方契约的本质是"语义素材"——每条记录都要能溯源回原文（evidence），供人阅读或知识图谱复用，不必可执行。

四、LLM 角色与确定性边界

维度我方对方
LLM 由谁充当宿主 agent（豆包）经 --host-contract 一次性交卷；Python 不读 SMINI_LLM_*、不发 HTTP宿主 agent（Claude Code / Codex / Cursor / WorkBuddy 通用）；AI 对话框的模型 API Key 由使用方自配
LLM 职责全部抽取语义：实体判断、关系识别、属性归属、规则/流程/六件套判定全部生成语义：需求探索提问、规格编写、七模型 YAML 建模、代码实现
确定性代码只做映射与兜底（枚举校验、ID、span、去重），不承担任何语义判断承担执行：规则求值（simpleeval）、流程推进、权限校验、DDL 生成
失败行为宿主未交卷 → 空结果 + 降级登记（no_credential），绝不造假未确认 → 硬暂停，绝不越阶段；AI Key 未配置 → AI 对话框降级为不可用，系统其余功能正常

七、逐维度优劣

我方优势

  • 轻量敏捷：零外部依赖，单条命令端到端（build → validate → render），适合"拿到文档立刻知识化"。
  • 语义灵活：契约即规则——抽取语义全部交给宿主 LLM，无正则/无模式清单，天然适应任意领域文本；19 类实体枚举（含 7 类金融扩展）直接服务金融场景。
  • 抽取深度：十一件套（含 v6 状态机/函数/时态/动作/约束/授权六件套）直指本体驱动的预测与决策，这是对方没有的通道。
  • 证据可追溯：每条产出带原文 evidence，validate 保证枚举/引用合法，138 单测兜底。
  • 可视化即读：每次生成 JSON 同步产出自包含 HTML 查看器（关系图谱/状态机 SVG/流程 SVG/传导列），零依赖离线可开。

我方劣势

  • 产物不可执行：rules 的 condition/action 是自然语言字符串，processes 是描述性步骤——不能跑，不能驱动任何运行时。
  • 无领域建模深度：实体扁平（无聚合/外键/字典/生命周期），没有行为模型与界面模型，无法回答"系统怎么建"。
  • 无人工门禁：抽取质量一次成型，错误依赖事后 validate/人工发现，高风险场景缺少需求确认缓冲。
  • 类型封闭：19 类实体枚举对超领域内容（如工程图纸、医疗文书）覆盖有限。

对方优势

  • 端到端真产物：需求一句话 → 可运行 BS 系统（含流程引擎、权限、报表、AI 对话框），价值闭环最强。
  • 模型即可执行：M1→建表、M3→simpleeval 规则可跑、M6→流程引擎、M5→权限种子——"模型一套、代码一套"被从机制上杜绝。
  • 需求质量可控：8 阶段人工门禁 + A/B 类内容分级 + 47 项自检，企业级误判风险显著降低。
  • 可移植性强：声明兼容 Claude Code / Codex / Cursor / WorkBuddy 多工具，自带 techbase 底座复制即用。
  • 七模型覆盖面：对象/行为/规则/主体/流程/报表/UI 七面齐备，是完整应用工程语义。

对方劣势

  • 重：npm/pip 依赖、底座复制、构建周期长；对"把文档知识化"这类轻任务严重过载。
  • 场景单向：只服务"要建系统"；对已有系统文档（如理赔需求说明书）的语义抽取与知识沉淀无能为力。
  • 表达受限于可执行性：规则必须写成 simpleeval 表达式，模糊/叙述性规则（如"综合评估风险承受能力"）难以入模；M3 规则无法承载道义模态与开放性条件。
  • 学习与遵循成本高：5 份规范 274KB 强制遵循，新人上手门槛高。
  • 人工成本高：8 阶段硬暂停，小需求也要走完整确认链路。

九、互补性与演进建议

两者不冲突，可形成"文档语义 → 系统构建"的互补链路：

  • 输入互补：对方阶段一（需求探索）前，可用我方抽取已有业务文档/制度/历史需求，快速产出领域实体、规则、流程、权限基线，作为对方附录 C 建模输入基线的候选种子，压缩人工探索轮次。
  • 通道互补：我方的 rules（道义模态、开放式条件）可补对方 M3 规则（仅可执行表达式）覆盖不到的规范性内容；我方的 processes/states 可辅助对方 M6 流程与 M1 生命周期的初稿。
  • 反向沉淀：对方产出的系统（模型+代码）若需文档化/知识化，可用我方对其需求文档、模型 YAML 做抽取沉淀，形成可查询的知识资产。
  • 架构同构启示：双方殊途同归地选择了"宿主 LLM + 结构化契约 + 确定性消费层"的边界，说明这是 Skill 化本体工程的稳健范式；差异只在"契约是语义素材还是可执行规格"。

一句话结论

我方赢在"轻、深、可溯源"（把文档读成本体知识），对方赢在"全、实、可执行"（把需求建成真系统）；前者是本体工程的"读端"，后者是"建端"。若要二选一，取决于终点是"知识"还是"系统"；若要最大化价值，应让两者串联。
