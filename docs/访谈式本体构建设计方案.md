# 访谈式本体构建（Interview-driven Ontology Building）设计方案

> 状态：**设计待认可**（v1.1，2026-09-20）
> v1.1 增补（用户评审意见）：**项目（Project）层落盘设计**——"项目"为持久化一等单元，
> 访谈/文档抽取均为项目下的"来源"，追加访谈 = 在项目累计模型基础上开新会话、收尾后归并。
> 核心原则：契约即规则（Rule-by-Contract）、尽量声明式大模型、尽量少确定性 Python、宿主 agent（豆包）充当 LLM。

---

## 1. 背景与目标

### 1.1 痛点

现有 smini-extract 的输入是**归一化文档**：宿主读文档 → 按契约交卷 → 薄壳校验。但现实中有两类情况文档无法满足：

1. **无文档**：项目刚启动，只有业务方/领域专家脑子里的信息；
2. **文档不全**：文档覆盖了制度流程，但缺少实际做法、例外情形、角色分工、系统边界等"活知识"。

这两类情况都必须靠**访谈（多轮对话）**获取信息。

### 1.2 目标

- 增加一个「访谈」功能：以多轮对话为信息源，逐步构建/完善本体模型（十一类契约本体）；
- 两种调起时机：
  - **独立启动**：用户说「开始访谈 XX 项目」，从零开始访谈建模；
  - **随时追加**：项目建立后，任何时刻可再次调起访谈，在**项目累计模型**基础上继续补充；
- 最终产物与文档抽取**完全同构**：一张宿主契约 JSON → 同一套 validate / 渲染 / 图谱；
- **新增项目层**：项目是跨来源（多次访谈 + 多份文档抽取）的持久化建模单元，所有来源归并到项目累计模型。

---

## 2. 核心思想：信息源替换 + 项目归集

```
现有管线（文档驱动，无项目）：
  文档 → 归一化 → [宿主读全文 → 按契约交卷] → 薄壳校验 → runs/<run_id>/04-extraction.json（孤立的 run）

访谈管线（对话驱动，有项目）：
  ┌─ 项目：projects/<项目名>/（持久化累计模型 + 来源清单）
  │
  ├─ 访谈来源：projects/<项目名>/interviews/<会话id>/（一次访谈 = 一个会话，收尾后归并入项目）
  │    用户回答 → [宿主看会话状态+项目累计摘要 → 增量delta + 下一问] → 薄壳合并 → 循环 → 收尾
  │
  └─ 文档来源：projects/<项目名>/runs/<runid>/（项目模式下的文档抽取，收尾后归并入项目）
```

**两种输入源（文档 vs 对话）只有摄取方式不同**；契约、薄壳校验、渲染、产物格式**全部复用**；
所有来源的产物最终**归并到项目累计模型**，项目因此可被"随时追加访谈"。

## 3. 现状对照（复用点盘点）

| 现有资产 | 位置 | 访谈如何复用 |
|---|---|---|
| 宿主契约格式（十一件事 + document_meta） | `skills/smini-extract/SKILL.md` §契约 | 访谈与项目的**产物格式完全一致** |
| 枚举与兜底（19 实体类、值类型、模态、flow_type、data_scope 等） | `smini/types.py` | 薄壳合并时做同样的枚举校验 + 非法兜底 |
| 宿主交卷注入机制 | `smini/llm.py::HostAgentLLMProvider` | 收尾时把累积契约 `inject()` 走同一薄壳 |
| 校验 | `smini/runtime.py::cmd_validate` | 访谈/项目产物走同一校验 |
| 渲染 | `skills/smini-extract/scripts/render_viewer.py` | 会话产物 + 项目总览渲染同一切口 |
| 抽取规则全集 | `references/extraction-rules.md` | 访谈的**判定规则直接引用**（宿主提问时按同一套规则核对缺口） |

**不新增**：不新契约、不新枚举、不新渲染器。只新增「项目层 + 会话状态管理 + 增量合并」这层薄壳。

## 4. 总体架构

```
┌─────────────────────────── 宿主 agent（豆包，充当 LLM 与对话前端）──────────────────────────┐
│                                                                                              │
│  ┌──────────────┐    首问/追问    ┌────────────────┐   用户回答    ┌──────────────┐          │
│  │ 项目/访谈控制  │ ──────────────▶ │   宿主 LLM      │ ◀──────────── │   用户        │          │
│  │ 器（薄壳）    │  ← 项目累计摘要  │  (提问/判定/    │ ── delta ──▶  │              │          │
│  │ ProjectManager│   会话状态/历史  │   增量交卷)     │               │              │          │
│  │ + InterviewStep│               └────────────────┘               └──────────────┘          │
│  └──────┬───────┘                                                                             │
│         │ 读写 projects/<项目名>/（项目 + 会话 + 来源）                                       │
│         ▼                                                                                     │
│  projects/<项目名>/
│  ├── project.json        # 项目状态：累计模型 + 来源清单 + 冲突（持久化一等单元）
│  ├── interviews/<sid>/   # 每次访谈会话（session.json + host-contract + html）
│  ├── runs/<runid>/       # 每次文档抽取（项目模式，结构与现有 runs 一致）
│  └── 04-extraction.html  # 项目累计模型总览渲染（可选）
│         │ 收尾归并
│         ▼
│  [归并] sources → consolidated（按锚点键并集 + 冲突登记）→ validate / 渲染 / 图谱
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

**职责划分（严格遵守契约即规则）**：

| 角色 | 负责 | 不负责 |
|---|---|---|
| 宿主 LLM（声明式） | 生成问题、判定收尾、产出模型增量（delta）、识别矛盾、评估覆盖度、识别项目语境 | 不做确定性校验、不算 ID、不落盘、不做归并 |
| 薄壳 Python（最小化） | 项目生命周期（建/开/列/归档）、会话落盘/恢复、delta 合并去重、ID 锚点稳定、枚举兜底、covered 统计、**来源归并（consolidate）**、收尾接线 | 不生成问题、不判断语义、不决定收尾 |

## 5. 项目层落盘设计（v1.1 新增 ★）

> "项目"是跨来源（多次访谈 + 多份文档抽取）的**持久化建模单元**。
> 一个项目 = 一份累计本体模型 + 来源清单；追加访谈 = 在累计模型上开新会话。

### 5.1 目录布局

```
projects/                                  # 项目根（与现有 runs/ 平级）
├── index.json                             # 项目注册表（列出全部项目，用于"打开/恢复/列表"）
└── <项目名>/                              # 以项目名命名的目录（可读；重名冲突加序号后缀）
    ├── project.json                       # ★ 项目状态（见 5.2）
    ├── interviews/
    │   └── <会话id>/                      # 每次访谈 = 一个子目录
    │       ├── session.json               # 会话状态（见 §6；初始态=项目累计模型）
    │       ├── host-contract.json         # 该会话收尾产物（宿主契约，与抽取同构）
    │       ├── 04-extraction.json         # 薄壳映射后的 ExtractionResult（可选保留）
    │       └── 04-extraction.html         # 该会话渲染
    ├── runs/
    │   └── <runid>/                       # 项目模式下的文档抽取（结构与现有 runs/<runid>/ 完全一致）
    │       ├── 03-normalized.json
    │       ├── 04-extraction.json
    │       └── 04-extraction.html
    └── 04-extraction.html                 # 项目累计模型总览渲染（consolidated 视图）
```

**向后兼容**：未点名项目的文档抽取**保持现状** `runs/<runid>/`；点名项目后才进入
`projects/<项目名>/runs/<runid>/`。现有 runs/ 结构、命令、产物格式全部不动。

### 5.2 project.json（项目状态）

```jsonc
{
  "project_id": "pv_8f3a...",           // ids.py 锚点哈希（name + created_at）
  "name": "适当性管理项目",               // 用户给的项目名（目录名）
  "domain": "金融/适当性",                // 领域（用于话术与完整性参考）
  "goal": "",                            // 建模目标（可选）
  "status": "ACTIVE",                    // ACTIVE | ARCHIVED
  "created_at": "...", "updated_at": "...",
  "active_session": "ivw_...",           // 当前未完成访谈会话（每项目最多一个 OPEN 会话）
  "sources": [                           // ★ 来源清单（可审计、可重建累计模型）
    {"kind": "interview", "ref": "interviews/ivw_xxx", "turns": 8,
     "status": "COMPLETE", "updated_at": "..."},
    {"kind": "document", "ref": "runs/run_xxx", "doc_id": "d-xxx",
     "status": "OK", "updated_at": "..."}
  ],
  "consolidated": {                      // ★ 累计本体模型（宿主契约格式，与 model_draft 同构）
    "entities": [...], "relations": [...], "attributes": [...], "rules": [...],
    "processes": [...], "states": [...], "functions": [...], "temporal": [...],
    "actions": [...], "constraints": [...], "permissions": [...],
    "document_meta": {"domain": "...", "source": "project://<项目名>"}
  },
  "covered": { "entities": 5, "relations": 3, ... },   // 累计计数
  "conflicts": [                         // ★ 跨来源冲突登记（锚点键撞车/语义矛盾）
    {"anchor": "rule:<主体>:<条件>:<动作>:<模态>",
     "between": ["interviews/ivw_xxx", "runs/run_xxx"],
     "issue": "两来源对该规则描述不一致", "resolved": false}
  ]
}
```

要点：
- `consolidated` 是**物化累计视图**：任何来源收尾后增量归并（见 5.3），并始终可
  **从 sources 清单重建**（校验用，命令式，不常用）；
- 条目级追溯靠各来源自己的 `host-contract.json` + `evidence`（用户原话/原文），
  项目层不做 per-item provenance 污染；
- `active_session` 保证"每项目最多一个进行中的访谈"，追加/恢复语义明确（见 5.4）。

### 5.3 归并规则（consolidate，确定性，薄壳实现）

把来源的宿主契约归并进 `consolidated`（与会话内 delta 合并同规则）：

| 类目 | 锚点键（唯一身份） | 归并行为 |
|---|---|---|
| entities | `canonical` | 并集；同 canonical 保留首见 surface，其余 surface 作为别名记录（不新增实体） |
| relations | `subject+predicate+object` | 并集；同锚点以最新来源为准（更新语义） |
| attributes | `entity+name` | 同 relations |
| rules | `subject+condition+action+modality` | 同 relations |
| processes | `name` | 同 relations |
| 六件套 | 各自既有锚点键（复用 types/extract 逻辑） | 同 relations |
| 同锚点、语义明显矛盾 | — | 保留最新来源值 + 登记 `conflicts`（unresolved），不静默覆盖 |

来源优先级：**时间戳靠后者胜**（访谈/抽取收尾顺序即时间序，`updated_at` 排序）。
归并后 `covered` 重算、`updated_at` 刷新；不通过就回滚并报告（原子性：先写临时文件再 rename）。

### 5.4 追加访谈语义（用户核心诉求 ★）

```
第 1 次：用户说「开始访谈 XX 项目」
  → 项目不存在 → 创建 projects/XX/（project.json，consolidated 空）
  → 新建会话 ivw_A（active_session=ivw_A；会话初始 model_draft = 项目累计模型 = 空）
  → 多轮对话 → 收尾 COMPLETE → 归并进 consolidated（sources +1）

第 2 次（一周后）：用户说「给 XX 项目再补充访谈一下」
  → 项目存在 → 读 project.json（consolidated + covered + agenda 摘要）
  → 检测 active_session：无 OPEN（上次已 COMPLETE）→ 新建会话 ivw_B
  → 会话初始 model_draft = 项目累计模型（携带 covered/canonical 摘要给宿主）
  → 宿主基于"已有什么"继续追问缺口（不重复已覆盖主题）
  → 收尾 COMPLETE → 归并进 consolidated（sources +1，锚点键无重复 → 无冲突）

中断恢复：会话 OPEN 未收尾 → 再次调起时提示
  「继续上次访谈（第 N 轮，待办主题：…）？还是开新会话？」
  → 继续 = 恢复 ivw_A；开新会话 = 先把 ivw_A 标记 ABORTED（保留轨迹），再建 ivw_B
```

**关键语义**：访谈会话**永远从项目累计模型起步**（除非项目是新建的）。
这就是"项目建立之后随时可以被追加访谈"的落盘保证——追加的不是空会话，而是带着项目已有知识的会话。

## 6. 数据模型：InterviewSession

落盘 `projects/<项目名>/interviews/<会话id>/session.json`，UTF-8，单文件：

```jsonc
{
  "session_id": "ivw_7f3a...",          // ids.py 锚点哈希风格
  "project": "适当性管理项目",           // 所属项目（必填，访谈强制挂靠项目）
  "project_ref": "projects/适当性管理项目", // 项目目录引用（恢复用）
  "domain": "金融/适当性",
  "goal": "",
  "status": "OPEN",                     // OPEN | CLOSING | COMPLETE | ABORTED
  "turn": 3,
  "model_draft": {                      // 十一类部分填充；初始 = 项目累计模型（见 5.4）
    "entities": [...], "relations": [...], "attributes": [...], "rules": [...],
    "processes": [...], "states": [...], "functions": [...], "temporal": [...],
    "actions": [...], "constraints": [...], "permissions": [...],
    "document_meta": {"domain", "source": "interview://<项目名>"}
  },
  "covered": { ... },
  "agenda": [ {"topic", "priority", "reason"} ],
  "asked": ["…"],
  "history": [ {"role": "host|user", "text": "...", "delta": {...}} ],
  "conflicts": [ {"target", "issue", "resolved": false} ],
  "meta": {"created_at", "updated_at", "source": "interview"}
}
```

与 v1.0 的差异：`model_draft` 初始值 = 项目累计模型；`project_ref` 提供项目级恢复锚点。

## 7. 交互流程（时序）

```
用户: 开始访谈「XX项目」                        (触发词见 §11)
宿主: 项目不存在 → 建项目；或项目存在 → 读累计摘要
薄壳: 建会话（初始 model_draft = 累计模型）→ 宿主首问（领域+目标+缺口盘点）
用户: 回答1
宿主: 组装「项目累计摘要(covered/canonical) + 会话状态 + 回答1」
       → LLM 产出 { delta, next_question, closing, note }
薄壳: 合并 delta → model_draft → 更新 covered/agenda → 落盘 session.json
      → 进度 note（"已记录 2 个新实体、1 条规则"）
用户: 回答2 …（循环）
宿主: LLM 判定 closing=true（覆盖度达标）或用户说「结束/够了」
薄壳: status=COMPLETE → host-contract.json 落盘
      → 归并进项目 consolidated（sources +1，冲突登记）
      → 项目累计模型渲染（04-extraction.html）+ 会话渲染
      → （可选）cmd_validate
```

## 8. 提问策略（声明式规则，写进访谈提示词）

宿主 LLM 按下述规则生成问题，Python 侧**零实现**：

### R1 缺口驱动（最高优先）
对照 `covered` 与完整性参考（十一类各自的最低期望，见下），**优先问缺口最大的维度**。完整性期望（声明式，LLM 自行判断"是否适用"而非机械凑数）：

| 维度 | 最低期望（若领域适用） | 判断线索 |
|---|---|---|
| entities | ≥ 3（主体/角色/系统/客体） | 谁参与、被处理、被管理 |
| relations | ≥ 2 | 实体间的职责/依赖/控制/从属 |
| attributes | ≥ 2 | 实体有可量化的属性（等级/金额/期限/状态） |
| rules | ≥ 2 | 有"应当/不得/如果…则"的业务规范 |
| processes | ≥ 1 | 有顺序执行的动作链 |
| 六件套 | 按需 | 有状态演化→states；有计算公式→functions；有时间限定→temporal；有处置动作→actions；有结构约束→constraints；有权限→permissions |

**追加访谈时**：缺口 = 项目累计 covered 与完整性参考之差；已覆盖主题不再重复提问。

### R2 主题聚焦
一轮只推进**一个主题**（实体盘点 → 关系 → 属性 → 规则 → 流程 → 六件套），不在一个问题里混多个主题；连续追问同一实体时给用户"可以只说不知道"的出口。

### R3 追问链
对用户新提到的关键实体，优先追问其**属性**（等级/金额/期限/状态）与**关系**（与谁协作/由谁负责/受谁约束），而不是立刻跳到新主题。

### R4 确认式提问
对高风险结论（关键规则、审批链、授权范围）做**反查确认**：「我理解到……是这样吗？」；发现 `conflicts`（会话内或项目内 unresolved）时，下一轮优先让用户裁决。

### R5 领域话术
`domain=金融` 时，问题模板偏向：客户/产品/机构、适当性/风险/合规、审批链/授权/数据范围、指标与公式（金融领域扩展枚举的触发词表复用 extraction-rules.md §12）。

### R6 问题卫生
- 一次一问，问题具体、可回答（不用"还有什么要补充的吗"这类开放到无效的问题）；
- 不重复 `asked` 中已问过的问题（除非为确认冲突）；
- 问题配一句"为什么问"（让用户理解意图，提高回答质量）。

## 9. 收尾判定（声明式）

满足任一即进入收尾（CLOSING，先给用户一次"还有要补充的吗"的机会）：

| 条件 | 说明 |
|---|---|
| 用户显式结束 | 「结束 / 够了 / 先这样」 |
| 覆盖度达标 | LLM 自评：十一类中适用的维度已覆盖、无重大缺口、无未决冲突 |
| 议程耗尽 | `agenda` 已全部推进完毕 |
| 轮数保护 | 达到上限（建议 20 轮）时提示「信息已较充分，可结束；若需继续可说明还想覆盖的方面」 |

收尾动作（薄壳）：`model_draft` + `document_meta.source="interview://<项目名>"` → 落盘 host-contract.json
→ **归并进项目 consolidated** → 会话渲染 + 项目总览渲染。**不要求宿主重新生成一遍完整契约**。

## 10. 薄壳职责（Python 最小化清单）

新增 `smini/steps/project.py`（`ProjectManager`）与 `smini/steps/interview.py`（`InterviewStep`），职责仅限：

**ProjectManager**
1. `create(name, domain, goal?)` → 建目录 + project.json（idempotent：已存在则打开）；
2. `open(name)` / `list()` → 读 index.json / 项目状态（恢复用）；
3. `append_source(project, ref, contract)` → 按 §5.3 归并进 consolidated + 冲突登记 + covered 重算；
4. `rebuild(project)` → 从 sources 清单重算 consolidated（校验用）；
5. `archive(name)` → status=ARCHIVED（保留数据）。

**InterviewStep**
1. 会话生命周期：创建/读取/更新/落盘 `interviews/<sid>/session.json`；状态机 OPEN→CLOSING→COMPLETE/ABORTED；
2. **会话初始化**：初始 model_draft = 项目 consolidated（新增项目时空）；
3. **delta 合并**：宿主每轮交卷的 `delta` 合并进 `model_draft`（新增条目按现有 ID 锚点规则生成 ID；同锚点重复 → 更新而非追加；枚举非法 → 兜底；下标越界 → None/丢弃，均复用 extract 同款逻辑）；
4. covered 统计与 agenda 透传；
5. conflicts 登记（会话内 unresolved 透传给宿主；收尾时并入项目级 conflicts）；
6. 收尾接线：COMPLETE → host-contract 落盘 → ProjectManager.append_source；
7. 进度反馈：每轮一行 note（新增了几实体/几关系/几规则）。

**薄壳不做**：不生成问题、不判断覆盖度、不决定收尾、不解释语义。

## 11. 三种触发模式（项目语境）

| 模式 | 触发指令（示例） | 行为 |
|---|---|---|
| **新建项目+访谈** | 「开始访谈 XX 项目」「为 XX 项目访谈建模」 | 项目不存在 → 创建 → 新会话（空起步） |
| **追加访谈** | 「给 XX 项目再补充访谈」「XX 项目访谈补充一下」 | 项目存在 → 新会话（初始=累计模型）或恢复 OPEN 会话 |
| **文档抽取（项目模式）** | 「把这份文档抽到 XX 项目」「为 XX 项目抽取」 | 产物写入 projects/XX/runs/<runid>/ → 归并入项目 |
| **混合模式** | 访谈中粘贴文档片段：「这是相关制度，你看下」 | 片段按文档增量并入本轮 delta（作为"回答+文档"合并输入） |
| 无项目语境 | 只说「开始访谈」（未给项目名） | 宿主首问顺带收集项目名/领域；**访谈强制挂靠项目** |

触发判定写在 smini-interview SKILL.md 的 description 触发词区（与 smini-extract 并列）。

## 13. 决策点（请确认）

| # | 决策点 | 方案 A | 方案 B | 建议 |
|---|---|---|---|---|
| D1 | 承载形态 | **独立 skill `smini-interview`**（含项目生命周期 ProjectManager + 访谈） | smini-extract 内嵌"访谈模式" | **A**：职责独立、触发词独立、GitHub 发布单元独立；契约规范共享不复制 |
| D2 | 项目落盘形态 | **`projects/<项目名>/` 分层**（project.json + interviews/ + runs/ + 项目总览渲染） | 平铺进 runs/ 加项目标记 | **A**：项目是一等单元，追加/恢复/审计都清晰 |
| D3 | 项目注册 | `projects/index.json` 注册表（列项目/状态/更新时间） | 扫目录推断 | **A**：O(1) 打开/列表，支持重名处理与归档标记 |
| D4 | 归并规则 | 锚点键并集 + 时间戳靠后胜 + 冲突登记（§5.3） | 只并集不冲突登记 | **A**：矛盾不静默覆盖，可审计 |
| D5 | 访谈是否强制挂靠项目 | **是**（访谈必属项目，追加才有落点） | 否（可无项目孤立会话） | **A**：无项目的访谈无法追加，违背核心诉求 |
| D6 | 会话初始态 | **= 项目累计模型**（追加天然"接着问"） | 空会话、收尾才归并 | **A**：避免重复提问、保证追加连续性 |
| D7 | 追加时冲突处理 | unresolved 冲突下轮/下次优先裁决 | 自动取最新 | **A**：与 R4 确认式提问配套 |
| D8 | 混合模式 | **支持**访谈中吸收粘贴的文档片段 | 不支持 | **A**：现实中访谈常伴随"我给你看份材料" |

## 14. 风险与边界

| 风险 | 对策 |
|---|---|
| 访谈轮数失控 | 20 轮保护 + 用户随时可「结束/先这样」 |
| 用户回答空泛/跑题 | R2/R6：主题聚焦 + 引导式追问（给例子帮用户回答） |
| 前后信息矛盾 | 会话内 conflicts 登记 → 下轮优先裁决；跨来源冲突 → 项目级 conflicts，下次访谈/抽取时优先裁决 |
| 用户不耐烦 | 每次宿主先转述增量 note（"已记录…"）再提问，让用户看到进展 |
| 口头信息不如文档精确（数值/法条） | 提示用户"该处如有文档请补充"，走混合模式 |
| 项目目录中文名/特殊字符 | 文件名清洗（去掉 `/ : * ? " < > |`）；重名冲突 index.json 登记后缀 |
| 访谈内容含敏感信息 | 产物与文档抽取同等对待；图谱/渲染沿用现有隐私边界（仅本地） |

## 16. 验收标准（总）

1. 说「开始访谈 XX 项目」→ 创建项目 + 会话，发出首个有效问题；
2. 多轮对话后 `model_draft` 持续增长、covered 更新、无 ID 漂移；
3. **项目建立后随时追加**：再次调起 → 在累计模型基础上继续追问，收尾归并无重复、无静默覆盖（冲突有登记）；
4. 中断退出后再调起 → 恢复 OPEN 会话或开新会话（旧会话保留轨迹）；
5. 说「结束」或覆盖度达标 → 产出合法宿主契约（validate 通过）+ 会话 HTML + **项目总览 HTML**；
6. 项目模式下文档抽取归并入同一项目；非项目模式 runs/ 行为不变（向后兼容）；
7. 全程薄壳只做 §10 清单内的确定性工作，提问/判定/收尾/覆盖度评估全部由宿主 LLM 声明式完成。
